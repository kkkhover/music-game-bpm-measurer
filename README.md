## 1. 这是什么

一个帮你在**音乐游戏里做出准确 timing** 的桌面工具。核心用途：

1. 导入一首歌 → 看**波形 + 声谱**，听、对着节拍线找 BPM 变化点；
2. 一段一段地记录「BPM + 起始时间 + 拍号」（软件里叫**变速段落**，也就是谱面里的**红线**）；
3. 一键导出成各游戏/制谱器能直接用的 timing 文件。

它由两部分组成，**打包在同一个 exe 里**：

| 部分 | 作用 |
|---|---|
| **主程序**（BPM 测速助手） | 导入音频、测速、编排变速段落、导出 timing |
| **制谱侧栏**（osu-maphelper） | 做 osu! 谱面时贴在编辑器旁边：实时频谱/声谱、可拖的红线时间轴、跟随 osu! 播放位置、定时备份 |

侧栏**不需要单独安装**：主程序里点「制谱侧栏」就能拉起。

## 4. 主程序怎么用

### 4.1 界面构成

| 区域 | 说明 |
|---|---|
| 顶部工具条 | 「导入音频」、「制谱侧栏」、音量、**变速播放**（听慢速不改音高）、设置、帮助、当前播放时间、导出 |
| 主可视区 | 上方**波形**、下方**声谱**；叠着竖线：**红线**（BPM 变化点）、**绿线**（变速/节拍）、**拍线** |
| 底部播放条 | 播放/暂停、当前 BPM、缩放（像素/秒）、**跟随播放**开关（白条滑出视口时自动滚到下一区域） |
| 右侧「配置面板」 | 全局起始偏移 **OFFSET**、导出按钮、**变速段落列表**（索引号 / BPM / 起始时间） |

### 4.2 标准流程

1. **导入音频**（顶部按钮，或 `Ctrl+O`）——支持的音频由 Chromium 解码器决定，`.mp3 / .ogg / .wav / .m4a / .flac` 都行。
2. **对齐 OFFSET**：在「全局起始偏移」里填/微调这首歌的第一拍时间（秒）。右侧的「起始时间」会跟着整体平移。
3. **逐段编排**：
   - 在右侧「变速段落」里添加/编辑每一项（**BPM**、**拍号/索引号 BEAT**、**起始时间**）；
   - 左边时间轴上可以直接**拖动红线**改位置；波形/声谱用来判断"这一拍到底在哪"；
   - 变速播放（把速度降到 35% 左右）能明显提高找拍的准确度。
4. **核对**：底部显示**播放头所在段落**的 BPM；节拍线与实际鼓点对齐即说明该段正确。
5. **导出**（见 4.3）。

### 4.3 导出

点顶部「导出 JSON 配置」旁的下拉箭头，得到两类出口：

**A. 通用**
| 项 | 产物 | 用途 |
|---|---|---|
| 导出 JSON 配置 | `.json` | 本软件自己的工程配置（可再导入回来） |
| 导出 osu! TimingPoints | `.txt` | `[TimingPoints]` 段（红线 + 绿线），复制进 `.osu` |

**B. 其他音游**
| 项 | 产物 | 用途 |
|---|---|---|
| **Malody 谱面包（含音频）** | `.mcz` | **直接拖进 Malody 即可导入**（含音频，最省事） |
| Arcaea 自制谱 | `.txt` | `.aff` 的 Timing 段 |
| Phigros 自制谱 | `.txt` | `BPMList` |
| ADOFAI（冰与火之舞） | `.txt` | `SetSpeed` actions |
| vivid/stasis | `.txt` | `vschart.json` 的 timingPoints |

> **关于 Malody**：v0.8.15 起只保留「**谱面包**」这一条出口。
> 原因是 `.mc` 里只写音频的**文件名**，Malody 只在**该谱面文件夹里**找同名音频；
> 名字对不上它会静默退回约 1 秒的占位音源 —— 表现就是"**编辑器里音乐只有几秒钟**"。
> 谱面包把音频一起打包（包内音频名与 `.mc` 里的 `sound` 必然一致），从根上避免这个问题。
> 用法：导出后把 `.mcz` **直接拖进 Malody 窗口**即可。

### 4.4 快捷键（主程序）

| 按键 | 作用 |
|---|---|
| `Ctrl+O` | 导入音频 |
| `Ctrl+S` | 导出 JSON 配置 |
| `Ctrl+Z` | 撤销 |
| `Ctrl+Y` / `Ctrl+Shift+Z` | 重做 |
| `空格` | 播放 / 暂停 |
| `←` / `→` | 前后移动（按住 `Shift` 每次 ±5 秒） |
| `Alt+←` / `Alt+→` | 切到**上一段 / 下一段**（播放头移到段起点并居中，到头即停） |
| `+` / `-` | 时间轴放大 / 缩小 |
| `滚轮` | 横向滚动（按住 `Shift` 竖向） |
| `Shift+滚轮` | **粗调**频谱 px/s（每格 ×1.1），以光标位置为锚点 |
| `Alt+滚轮` | **精细**调频谱 px/s（每格 ±3%），用来在"看清某一拍"和"看全整段"之间微调 |
| `Delete` | 删除选中的红线 |

### 4.5 设置项（顶部齿轮）

- **主题配色**：预设主题、自定义颜色、强调色、背景/面板底色、波形色、频谱配色、峰值色
- **频谱**：FFT 精度（512 ~ 8192）、灵敏度、调色板（含自定义三段色）、对数频率刻度、反相、峰值阈值与颜色
- **节拍线延迟**：让节拍线与实际声音对齐（可设为「跟随软件」，直接采用测速助手里校准好的值）
- **拍号（meter）**（v0.8.17）：每个变速段落可设置「每小节几拍」（4 = 4/4、3 = 3/4），决定小节线与节拍器重音分组
- **渲染倍率**：画面清晰度 / 显存的取舍（调低可显著省内存）
- **节拍器音色**：电子 / 打击 / 柔和（可预览）
- **语言**：中文 / English / 日本語 / 한국어 等
- **重置**：恢复默认设置

## 5. 制谱侧栏怎么用

### 5.1 前置：跑起 tosu

侧栏**自己不读 osu! 内存**，而是向本机的 **tosu** 要数据：

```
GET http://127.0.0.1:24050/json/sc
```

所以使用前请先启动 tosu（默认端口 `24050`），并确认 osu! 正在运行、tosu 界面能看到当前谱面。
**tosu 没开 → 侧栏会一直显示"无音频/无数据"，这是正常的。**

### 5.2 打开方式

主程序里点「**制谱侧栏**」。它其实是同一个 exe 用 `--maphelper` 参数启动的第二个进程，
两者互不干扰。

### 5.3 面板

| 面板 | 内容 |
|---|---|
| **频谱（viz）** | 实时频谱 + 声谱 + 波形；时间轴上可**拖红线**；显示 osu! 播放位置（平滑跟随） |
| **map** | 当前谱面信息 |
| **backup** | 定时备份（把谱面文件夹里的 `.osu` 定期复制一份） |
| **settings** | 侧栏自己的设置（配色、缩放、轮询、面板位置…） |
| **log** | 运行日志 |

### 5.4 导出 timing（侧栏）

侧栏改完红线后，用 **`POST /api/timing/export`** 导出：

- 产物落在**数据根目录**下的 `exports\<谱面标识>-<年-月-日-时-分-秒>.osu`；
- **不会写回原谱面文件**（安全，不会污染你的谱面）；
- 导出采用 **merge 模式**：红线整体替换 + **每条红线后跟一条绿线**，绿线倍速 = **基准 BPM ÷ 当前 BPM**，
  这样 BPM 变化时下落流速保持恒定；
- 添加红线时，新红线严格落在「上一条红线的**下一拍**」。

### 5.5 快捷键（侧栏）

| 按键 | 作用 |
|---|---|
| `Ctrl+Z` / `Ctrl+Shift+Z` · `Ctrl+Y` | 撤销 / 重做 |
| `空格` | 播放 / 暂停预览 |
| `←` / `→` | 前后移动（按住 `Shift` 每次 ±5 秒） |
| `+` / `-` | 缩放 |
| `Ctrl+O` | 重新载入音频 |
| `Ctrl+S` | 导出 timing |
| `Delete` | 删除选中的红线 |
| `Alt+←` / `Alt+→` | 上一个 / 下一个面板 |

### 5.6 侧栏的语言（v0.8.17）

侧栏的 **settings** 面板底部有「**语言 / Language**」：

- 默认**跟随软件** —— 直接采用你在 BPM 测速助手里选的语言（中 / 英 / 日 / 韩 / 法 / 德 / 西 / 俄 / 葡）；
- 取消勾选后可**单独为侧栏**指定语言；
- 在测速助手里刚改完语言，点一下旁边的「**⟳ 重新读取**」立即生效（不点的话下一轮轮询也会跟上）。

侧栏与主程序是两个独立进程、各有各的配置目录，所以语言是靠主进程去读测速助手的设置来同步的。

| 导出的 timing 文件带注释导致游戏读不了 | JSON 类导出从来不带注释头；若你自己编辑过，注意别加 `//` |
| 旧 Malody 谱面打不开 | 旧格式（`beat` 全是 `[n,0,1]` 整数）仍可正常导入，向后兼容 |

## 7.5 低内存 / 高分屏机器的性能适配（本机已启用）

在 **8GB 内存 + 高分屏 + 核显** 的笔记本上（本机：Ryzen 7 255 / Radeon 780M、
2880×1800@200%、物理内存 6.8GB、系统提交内存常年 10GB+），原版会有明显的拖拽/缩放卡顿。
这一版做了针对性适配，**行为全部自动生效，不需要手动改设置**：

| 改动 | 原来 | 现在 | 为什么 |
|---|---|---|---|
| **渲染分辨率锁 1080p** | 按 `devicePixelRatio × 渲染倍率` 建画布（本机 = 2774×1634，每层 450 万像素） | 画布位图宽度**恒定 1920 设备像素**（1920×1153），与屏幕缩放/窗口大小无关 | 4 层叠加大幅超出核显共享显存能承受的量；锁 1080p 后像素量降到 48%，且分辨率可预期 |
| **频谱着色查表化** | 每个像素调一次配色函数（内含 5 个闭包 + hex 解析 + 数组分配 + `Math.pow`） | 预算成 256×512 的色表，每像素**只查一次表** | 一屏 224 万像素 × 上千万次临时对象分配 = GC 抖动 |
| **频率映射按行预算** | 每像素一次 `Math.pow` 求对数刻度 bin | 按行算一次，绘制时查表 | 省掉每像素 1 次 pow |
| **拍线合批** | 每根拍线/箭头单独 `beginPath+stroke+fill` | 按样式分组，每种样式**一次**描边/填充；拍线密到 <7px 时不再画箭头和编号 | 整曲缩略时一屏上千根线 → 上千次绘制调用 |
| **缩放只做变换预览** | 每按一次缩放就整幅重绘 | 缩放期间**不重绘**，仅对旧位图做合成层 `scaleX`（限幅 ±35%）；停手 160ms 后整幅重绘一次 | 实测一次整幅重绘的光栅/上传开销 0.6~2s，而 JS 只占几毫秒 |
| **单批绘制** | 频谱分 10 批、每批一次 `putImageData` | 一次性画完 | 每次 `putImageData` 都要重传整幅纹理，分批 10 次 ≈ 10 倍合成开销（实测 2000ms → 650ms） |
| **长曲跳过整曲预计算** | 每首歌都用 `OfflineAudioContext` 渲染整曲频谱 | 时长 > 4 分钟直接走逐列 FFT（单列 ~24µs，1920 列 ≈ 46ms，且有列缓存） | 7 分钟立体声要 150MB+ 音频缓冲，本机内存不够会直接卡死在换页上 |
| **位图/列缓冲复用** | 每列 `new Uint32Array`、每次重绘 `createImageData`（8.8MB） | 列缓冲池 + 按宽度缓存 ImageData | 缩放一秒能产生上百 MB 垃圾 → 大 GC |
| **总览条拆两层**（v0.8.18） | 迷你波形和视口高亮画在同一张 canvas，effect 依赖 `viewStart/viewEnd` → **拖动每前进一像素就重画一次整曲波形**，一次 `stroke()` 里 20 万条子路径 | 静态波形层（只依赖 peaks/尺寸，按显示列聚合，子路径数 ≈ 画布宽度）+ 动态层（视口高亮 + 播放头，每次几个矩形） | 单次 `SkCanvas::drawPath` 实测 940ms（GPU 进程光栅化），是拖动卡顿的真正元凶 |

另外：

- **播放头层限帧 60fps**（120Hz 屏上原本每 8.3ms 重绘一次覆盖整窗的图层），
  且**位置没变化时完全不重绘**（暂停时零开销）；
- **UI 刷新按时间降频**到 10fps；
- 窗口失焦/被遮挡时**不降频**（`backgroundThrottling: false` + 低配时关掉 Chromium 的原生遮挡检测）；
- 2D canvas 硬件加速**默认关闭**（本机实测打开更慢），需要时用环境变量 `BPM_CANVAS_GPU=1` 打开。

### 实测数据（本机，载入 7:09 的 Camellia - Parallel Universe Shifter）

| 场景 | 帧率 | 说明 |
|---|---|---|
| 空闲 / 播放中 | 100~120 fps | 播放头独立层，p95 ≈ 10ms |
| 拖拽平移（v0.8.18 修复后） | **110~120 fps，p50 8.4ms** | 长拖 900px / 100 次 mousemove：无 >100ms 帧；甩尾 200px/帧 也不掉帧 |
| 拖拽平移（v0.8.18 之前） | **1~2 fps，p50 838ms** | 每一步都被总览条的重绘堵住（详见 7.6） |
| 连续缩放（12 档连打） | **p50 ≈ 10ms** | 缩放期间零重绘；停手后一次回填 |

> 想更省性能：设置 → **渲染倍率** 拉到 `0.8`（位图 1536 宽）、FFT 精度保持 `1024`。

## 7.6 拖动卡顿的真正原因：总览条的「20 万条子路径」（v0.8.18 已修复）

7.5 里的改动把渲染侧的垃圾和纹理流量都压下去了，但**拖动频谱仍然一步一卡**（实测
1~2 fps、单帧 800ms+），而且 JS 侧只有几毫秒——说明卡在 GPU 进程，不在脚本。

用 CDP 抓 trace 才定位到根因（`RasterDecoderImpl::DoRasterCHROMIUM` 里全是 `SkCanvas::drawPath`）：

| 证据 | 修复前 | 修复后 |
|---|---|---|
| GPU 进程光栅化总耗时（一次拖动） | **5961 ms / 71 次** | **12.7 ms / 80 次** |
| 单次 `SkCanvas::drawPath` | **940 ms** | 已消失（无该事件） |
| 拖动帧间隔 p50 / max | 838 ms / 926 ms | **8.4 ms / 82 ms** |

原因：`components/OverviewBar.tsx` 把「迷你波形」和「视口高亮」画在同一个 effect 里，
而这个 effect 依赖 `viewStart/viewEnd`（= 频谱视口范围）。于是**拖动每前进一像素，整曲波形
就重画一次**。整曲峰值约 19 万个（`extractPeaks` 每 100 采样一个），旧代码给每个峰值
`moveTo` + `lineTo` 一条子路径 → 一次 `stroke()` 里塞进 20 万条子路径的巨型 Path。JS 建路径
只要几毫秒（所以 profile 上看不出问题），但这段路径要在 GPU 进程光栅化，实测单次 940ms，
合成器被彻底堵死。

修复（`components/OverviewBar.tsx`）：

1. **拆两层 canvas**：底层只画网格 + 迷你波形，依赖 `[peaks, duration, 尺寸]`——拖动、播放都不重画；
   顶层只画视口高亮 + 播放头，每次 `fillRect` + `strokeRect` + 一条竖线，成本 < 1ms。
2. **按显示列聚合**：只建「画布设备像素列数」条矩形（约 1800 条），每列取该区间内峰值的
   min/max。视觉和旧版一致（旧版 19 万条子路径本来就大量重叠），子路径数降到原来的 1%。
3. 用轴对齐矩形 `fill()` 代替 `stroke()`，并且尺寸变化走 `ResizeObserver` 重新聚合。

> 教训：**「一次 beginPath 里塞几万个图形」在 Canvas2D 上是隐形的性能地雷。**
> JS 侧看不出耗时，代价全在 GPU 光栅化，profiler 只显示「帧间隔变长」。
> 排查手段：CDP `Tracing`（类别 `gpu,skia`）→ 看 `SkCanvas::drawPath` 的次数和耗时。

## 7.7 导入 timing 之后才卡的三个隐藏热点（v0.8.18 已修复）

现象：单纯播放还算顺，但**一旦导入 .osu 的 timing（几百个变速段），整个界面就拖不动**，
白色播放头条也一顿一顿。

量化结果（`dev-tools/bench-timing.mjs`，同一台机器、同一首 7:09 的曲子）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 导入 timing 后的呈现帧率 | **19.7 fps** | **55~61 fps**（受环境合成节奏限制，见下） |
| 播放中逐帧间隔 p99 / max | 大量丢帧 | **18.2 ms / 19.9 ms，0 帧 > 20 ms** |
| 播放期间覆盖层重绘 | **10 次/秒 × 全幅 2134×1282** | **0 次**（只有总览条的 10Hz 小图在动） |

三个热点和对应改法：

1. **播放头是「整窗 canvas 里擦一列」**。`2134×1282 ≈ 10.4 MB` 的位图，即便只改 13px 宽的一列，
   Chromium 也要把整张纹理重新上传给合成器 —— 每次约 8~12 ms，播放头最高只能到二三十帧。
   改成 **14px 宽的 DOM 合成层 `<div>`**，位置用 `translate3d()` 写，只在位置真正变化时赋值；
   移动完全走合成器，不重光栅、不上传纹理。
2. **覆盖层每帧整幅重画**。拍线层 1282px 高，原来被各种 effect 依赖带着每帧重绘一次。
   现在加了「参数 + 视口 + 拍点对象」四元组比较：**完全一致就整段 return**；
   只有 `scrollLeft` 平移时才走「旧内容平移 + 只补边缘条」的快路径。
3. **侧栏 timing 卡片跟着 10Hz 时间码重渲染**。播放时 `setCurrentTime` 每 100ms 触发一次全树
   re-render，500+ 张卡片的 2000+ 个 input 全部重建。现在 `TimingRow` 用 `React.memo` 包起来，
   且 props 只依赖自己那条 timing 数据 —— 播放时侧栏零重渲染。

另外两处交互修复：

- **导入音频要两次**：顶栏按钮是 `<label>` 包 `<input type=file>`，点它**系统文件框已经弹过一次**；
  旧代码不管 `e.target.files`，一律又走 `electronAPI.openAudioFile()` 再弹一次，于是第一次选的文件被丢弃。
  现在只要 `e` 里带了文件就直接用；同时解码期间按钮显示「解码中…」（7 分钟的歌要 1~3 秒），
  避免用户以为没反应而重复点击。
- **缩放倍率可键盘输入**：底栏 `px/s` 数字变成可编辑输入框，直接键入 30~2000 之间的值，
  `回车`/失焦生效、`↑↓` 以 1.2 倍步进、`Esc` 撤销，缩放以**视口中心**为锚点。

> ⚠️ 关于「帧率数字」：本机是 120Hz 屏，但 Chromium 只在窗口是系统前台窗口时才把合成节奏
> 拉到 120Hz；窗口在后台时固定 60Hz。自动化测量（CDP）很多时候拿到的就是 60Hz 那一档，
> 所以上面的 55~61 fps 是**保守值**，不代表上限。真正要看的是「有没有丢帧」——
> 播放中 0 帧 > 20ms、拖动无 > 100ms 帧，就是这个指标达标了。

## 7.8 播放头滑出视口后自动跟随（v0.8.18 新增，默认开启）

长曲目（7 分钟 × 250 px/s ≈ 10 万像素宽）一屏只放得下 4 秒左右，播放时白条几十秒就跑到
视口外，旧版本只能手动拖时间轴去追。现在默认开启**跟随播放**：

- 白条越过视口右侧 **90%** → 视口**直接跳到**下一区域（一帧到位，与侧栏点段一致，**没有滚动动画**），
  白条落回左侧 **10%** 继续播；
- **手动拖动 / 滚轮滚动视口会自动关闭跟随**（否则想翻到头看一眼前奏，下一帧就被拽回来），
  随时点底栏最右侧的定位图标重新开启；
- 停止、点跳转、缩放都会中止当前跟随状态，不会出现「按旧比例算出的目标位置」。

### 为什么最终做成「瞬跳」而不是滚动动画

> 源码注释里的 `v0.8.19`~`v0.8.21` 是开发期间的内部标记，**均已并入 0.8.18 发布版**。

中途曾用「每帧推进 4% 视口宽、约 0.35 秒滚完一屏」的方式规避瞬跳那一下的卡顿。
后来明确要求**不要动画，像侧栏切段那样直接跳**，所以改回瞬跳，并把跳页那一帧的成本压下来：

| 方案 | 翻页瞬间最长帧 | 播放帧率 | 观感 |
|---|---|---|---|
| 最初（纯瞬跳，未降本） | 126~155 ms | 60 fps，每次翻页垮一次 | 每次翻页明显卡一下 |
| 中途试过（分帧滚动） | 与普通帧同档 | 117 fps | 平滑，但不是瞬跳 |
| **现行（瞬跳 + 降本）** | **59~67 ms** | **115.9 fps**，p99 9.6 ms | 一帧到位，只剩一次轻微顿挫 |

压下来的关键改动：频谱兜底路径（长曲不做整曲预计算时走这条）原本每列每行都算
`20*Math.log10(mag)`，一屏 2134 列 × 1282 行 = 2.7M 次 log10，实测光这一步就 60 ms。
现在改成「把 Float32 位模式的高 16 位当索引、直接查 dB 量化表」（`buildDbQuant`），
同样的工作量降到 6 ms 级。剩下的 ~60 ms 是一次整屏 `putImageData` + 一次画布平移拷贝，
属于这块核显（Radeon 780M、共享显存）的固定成本，瞬跳与侧栏切段同价。

> 试过但**不可行**的方案：把「视口右侧一屏」提前算进列缓存（预取）。列缓存键是
> `sampleIdx`，而翻页时画布按 `Math.round(dx)` 整数平移、`xToTime` 用未取整的
> `scrollLeft`，两者相差 **0.5 个设备像素**（实测键值 369145 vs 369081，步长都是 96 采样）
> → 命中率恒为 0。要修就得让滚动量对齐设备像素网格，或改成离屏画布整体 blit，
> 复杂度和风险都高于收益（60 ms 已低于用户可感知阈值），故放弃。

另外修掉一个存量 bug：白条 `<div>` 初始 `opacity: 0`，而 rAF 里 `visible` 变量初值是 `true`，
首帧不会走「点亮」分支 —— 只要播放头没先出界再回来，**白条就一直是透明的**。现在初值改成
`false`，首帧进视口即点亮。

验收脚本：`dev-tools/verify-follow.mjs`（跟随是否发生、是否一帧完成）、`verify-follow-toggle.mjs`
（拖动关闭/重开）、`probe-play.mjs`（帧间隔）、`trace-jump.mjs` / `profile-jump.mjs`（长帧归属）、
`probe-jump.mjs`（逐层绘制耗时）。

## 7.9 播放中点频谱/白条：停在点的位置（v0.8.18 修复）

**症状**：播放中点击频谱（或白条附近）后，声音继续放，但播放头、时间码、总览条**全部冻住**，
一直到最后都不会自己停。

**原因**：`handleSeek` 里写的是 `stop() + play()` 想「从新位置无缝续播」。两者在同一个事件里被
React 批处理成 `isPlaying: false → true`（最终值仍是 `true`），播放循环的 effect 因此**不会重建**，
而 `stop()` 已经把当前 `requestAnimationFrame` 取消了 —— 声源换成了新的（声音确实跳到新位置），
但驱动播放头的循环再也没人启动。

**修法**：
- 新增 `startSourceAt(t)`：只换 `AudioBufferSourceNode` + 重锚墙钟起点，**不碰 `isPlaying`、不重建循环**；
- `handleSeek` 默认行为改成**播放中点击 → `stop()` 停在该位置**（用户预期是「点了就停在这儿」），
  段间导航（`Alt+←/→`、侧栏点段）传 `{ keepPlaying: true }` 走 `startSourceAt`，跳过去继续放；
- 暂停后按播放从点击位置继续（实测 2.3 s → 播 0.7 s 到 3.0 s）。

验收脚本：`dev-tools/probe-seek.mjs`（播放中点击 → 时间码/播放头/播放状态）、
`verify-seek-resume.mjs`（续播位置、切段不中断）、`verify-pause-on-click.mjs`
（播放中点一下 → 必须暂停且 1.2 s 内时间码/播放头纹丝不动）。
