# BPM 测速助手 — 笔记本卡顿诊断报告

> 设备：Intel i5-12450H（4P+4E 核）+ RTX 4050 独显（Optimus 混合显卡）
> 现象：拖频谱图只有约 20 帧，明显卡顿
> 结论：**并非单一 bug，而是「高分屏 dpr 放大 × 每像素重计算 × GPU 后端选错」三重叠加**，在混合显卡笔记本上被放大。

---

## 一、硬件特点（为什么偏偏笔记本卡）

| 因素 | 说明 |
|---|---|
| **混合显卡** | 12450H 内置 Intel UHD 核显，另有 RTX 4050 独显。Chromium/Electron 默认**优先走核显**，4050 常处于闲置 |
| **高分屏** | 笔记本常见 2.5K/4K 屏，`devicePixelRatio` = 2.0~2.5，所有 canvas 像素量 ×4~6 |
| **核显带宽低** | Intel UHD 共享内存做显存，`putImageData` 大量像素上传时带宽远不如 4050 独显 |
| **单线程 JS** | 频谱逐像素计算全在主线程，8 核里只有 1 个核在跑，P 核单核再快也扛不住 224 万像素的重计算 |

---

## 二、根因逐项分析（按影响排序）

### 🔴 根因 1：每像素做了「全套重计算」，无任何预计算缓存
**文件**：`components/Visualizer.tsx` 的 `drawSpecRegion` + `utils/settings.ts` 的 `spectrogramColor`

拖频谱的全量渲染，每个像素都执行：

```js
// 每像素 1 次浮点 pow（对数刻度映射）
const binF = ((Math.pow(base, yNorm) - 1) / (base - 1)) * (numBins - 1);
// 双线性插值：4 次 Uint8 读 + 4 次乘加（v0.7.4 新增，为清晰度付出的代价）
// 然后 spectrogramColor(val, freqNorm) 内部：
//   - interpStops(stops, f)   多段色标线性插值
//   - Math.pow(v, 0.55)        gamma
//   - Math.pow(peakT, 0.6)     峰值陡峭过渡
//   - hexToRgbArr(peakColor)   ⚠️ 每像素重复解析同一个 hex 字符串！
```

**像素量估算**（高分屏 dpr=2，容器 1400×900）：
- `fullWidth = 1400 × 2 = 2800`，`fullHeight = specHeight(~400) × 2 = 800`
- 全量渲染 = **224 万像素**，每像素 100+ 次浮点运算 ≈ **2 亿+ 运算/次**
- 分帧 60 列/帧 → 4.8 万像素/帧，每帧近 500 万运算，叠加 putImageData 上传，16ms 帧预算被击穿

**根因 1 本质**：`Math.pow`、色标插值、hex 解析、gamma 这些「每像素相同、与列无关」的东西，全都应该**预计算成查找表（LUT）**。

---

### 🔴 根因 2：GPU 参数与逐像素渲染模式冲突（4050 没用上反而更慢）
**文件**：`main.ts` L13

```js
app.commandLine.appendSwitch('enable-accelerated-2d-canvas');
```

这是 v0.6.8 的参数。但频谱渲染是 **`putImageData` 逐像素写入** 模式——每次 `putImageData` 都要把整块像素数据从 CPU 内存**上传到 GPU 显存**。在 4050 独显上，这个「上传纹理 → 光栅化 → 显示」的往返比直接 CPU 写内存**更慢**。

> 这一结论在 v0.6.9 已经诊断并修复过（改成 `disable-accelerated-2d-canvas`），但当时用户否定了 v0.6.9 的全部改动，回退到了 v0.6.8，**这个正确的修复被一并丢弃了**。

**根因 2 本质**：`enable-accelerated-2d-canvas` 对 `putImageData` 密集型渲染是负优化，且混合显卡下 GPU 选择不受控（`prefer-integrated-gpu=false` 语义有限，实际由 Windows 图形设置决定，4050 很可能根本没被 Chromium 使用）。

---

### 🟠 根因 3：dpr 盲目跟随屏幕缩放，高分屏像素暴增
**文件**：`App.tsx`（Visualizer 的 `renderDpr` 传入）

```js
renderDpr = settings.renderQuality === 'performance' ? 1 : window.devicePixelRatio
```

- 默认「自动」模式 = `devicePixelRatio`，高分屏 2.0~2.5 → 像素量 ×4~6
- 「性能优先」模式才 dpr=1，但**默认不是它**，用户不主动开就一直是满 dpr
- 拖拽/缩放这种**动态交互过程**，其实 1.0 dpr 完全够看，停下后再恢复高清即可（AU 等软件就是这么做的）

---

### 🟠 根因 4：缩放（zoom）每次触发全量重渲染
**文件**：`components/Visualizer.tsx` 频谱 effect

- 平移（拖拽）已有优化：只重算露出边缘列 ✓
- 但 **zoom 变化 → 全量重绘**（`sameParams` 里含 zoom），滚轮缩放下每格都触发 47 帧的分帧重算，观感就是「缩放时卡成 PPT」
- 缩放过程无「降采样/临时低清」策略

---

### 🟡 根因 5：`extractPeaks` 白算一遍（decode 时）
**文件**：`App.tsx` L338 + `components/Visualizer.tsx` 波形绘制

- decode 后 `extractPeaks(decodedBuffer)` 算好波形峰值存进 `peaks`
- 但波形绘制 `drawColumns` 根本没读 `peaks`，而是**重新用 rawData 逐列扫 min/max**
- decode 那次峰值计算纯属浪费（虽然只一次，但暴露了「波形峰值」该复用没复用）

---

### 🟡 根因 6：多层 canvas + 播放头每帧全层擦除
**文件**：`components/Visualizer.tsx`

- 4 层 canvas（波形 / 频谱 / 刻度拍线 / 播放头），每层独立
- 播放头层每帧 `requestAnimationFrame`，虽然只擦旧列+画新列，但在 dpr=2 下每次 clearRect 的是整条竖带，开销可控但可进一步用 CSS 定位元素替代

---

## 三、优化方案（分优先级，先不改，待确认）

### 🥇 P0 — 立即见效、改动可控

**P0-1：去掉 `enable-accelerated-2d-canvas`（根因 2）**
- 改法：`main.ts` 删除该行（或改为 `disable-accelerated-2d-canvas`）
- 预期：`putImageData` 走 CPU 光栅化，省掉每帧纹理上传到 4050 的往返，拖频谱帧率明显回升
- 风险：低；这是 v0.6.9 已验证过的正确方向

**P0-2：颜色 LUT 预计算（根因 1 主因）**
- 改法：`spectrogramColor` 结果预计算成 `Uint32Array` 查找表——把 `val` 量化到 256 级、`freqNorm` 量化到 256 级（或按行），得到 256×256 色表；每像素从「100+ 浮点运算」降到「1 次数组查表」
- 预期：像素着色环节提速 10~50 倍，全量渲染耗时大幅下降
- 风险：低；色表在参数（palette/peakColor 等）变化时重建一次即可

**P0-3：对数 bin 映射 LUT（根因 1 次因）**
- 改法：`Math.pow(base, yNorm)` 的 binF 只与 `y`（行）有关，与列无关 → 预计算 `binLUT[fullHeight]`（存 b0/b1/bFrac），每列复用
- 预期：每像素省 1 次 pow + 重复的 bin 索引计算
- 风险：低

### 🥈 P1 — 高分屏与动态交互优化

**P1-1：dpr 上限 + 交互降 dpr（根因 3）**
- 改法：`auto` 模式 dpr 上限 1.5；拖拽/缩放进行中临时降到 1.0，空闲恢复
- 预期：高分屏像素量减半以上，交互帧率显著提升
- 风险：中（需处理 dpr 切换时的画布重建）

**P1-2：缩放降采样（根因 4）**
- 改法：zoom 变化时先按 1/2 精度快速渲染一版，空闲（rAF 空闲/防抖）再补全高清
- 预期：缩放过程流畅
- 风险：中（需引入「低清→高清」两阶段渲染状态）

### 🥉 P2 — 架构级优化（更彻底，改动较大）

**P2-1：频谱整曲预渲染成离屏大图 + 滚动 drawImage 切片**
- 预计算完成后，把整曲频谱渲染成一张离屏 canvas（或分块 ImageBitmap），滚动/缩放时直接 `drawImage` 切片，彻底脱离逐列 `putImageData`
- 预期：滚动零计算，只走 GPU blit；这是波形平移复用的「频谱版」
- 风险：高（内存占用大，需分块 + 懒加载 + dpr 取舍）

**P2-2：列计算移入 Web Worker**
- bin 映射 + 颜色 LUT → 生成 Uint32 列，Worker 并行算，主线程只 `putImageData`
- 预期：利用多核，主线程彻底不卡
- 风险：中（Worker 通信 + 缓存同步复杂度）

**P2-3：播放头层改 CSS 定位元素**
- 用绝对定位的 `<div>` 代替每帧 canvas 重绘播放头
- 预期：省一层 canvas 的每帧操作
- 风险：低~中

---

## 四、建议实施顺序

1. **第一批（P0 三项一起做）**：去 `enable-accelerated-2d-canvas` + 颜色 LUT + bin LUT → 预计拖频谱从 ~20fps 回到 50fps+
2. **第二批（P1）**：dpr 上限 + 缩放降采样 → 高分屏/缩放场景补强
3. **第三批（P2）**：视前两批效果决定是否上 Worker/整曲预渲染大图

> 说明：本报告仅定位原因，未做任何代码修改。确认方案后再动手。
